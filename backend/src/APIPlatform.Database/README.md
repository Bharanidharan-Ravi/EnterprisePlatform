# APIPlatform.Database

Provider-agnostic database access for EnterprisePlatform. Dapper is the execution layer; SQL
Server and SAP HANA are supported today, each behind its own `IDatabaseProvider`.

```
API / Repository
      ↓
IDatabaseExecutor / IStoredProcedureExecutor
      ↓
Dapper
      ↓
IDbConnection
      ├── SqlConnection  (Microsoft.Data.SqlClient) → SQL Server
      └── HanaConnection (Sap.Data.Hana.Net)         → SAP HANA
```

No type outside `Providers/SqlServerDatabaseProvider.cs` and `Providers/HanaDatabaseProvider.cs`
references `SqlConnection` or `HanaConnection` — every other type in the package, and every
consumer, works exclusively through `IDbConnection`/`IDatabaseExecutor`/`IDatabaseTransaction`.

## Registration

```csharp
// SQL Server
services.AddSqlServerProvider();
services.AddDatabase(options => configuration.GetSection("Database").Bind(options));

// SAP HANA
services.AddHanaProvider();
services.AddDatabase(options => configuration.GetSection("Database").Bind(options));
```

`AddDatabase()` itself registers no engine — call the matching `AddXxxProvider()` first. A host
that talks to more than one engine at once (e.g. mid-migration) can call both; the active one is
selected at runtime by `DatabaseOptions.Provider` through `IDatabaseProviderFactory`.

## Configuration

```json
"Database": {
  "Provider": "SqlServer",
  "ConnectionString": "Server=...;Database=...;User Id=...;Password=...;TrustServerCertificate=True;"
}
```

```json
"Database": {
  "Provider": "Hana",
  "ConnectionString": "Server=<host>:<port>;UserName=<user>;Password=<password>;"
}
```

APIPlatform.Data never reads `appsettings.json` itself — the consuming application binds
`DatabaseOptions` and passes it to `AddDatabase()`. Connection strings are configuration values
only; never commit real credentials, and `DatabaseConnectionFactory` never logs the connection
string itself, only the configured `DatabaseProvider` name, when wrapping open failures.

## Usage

```csharp
public sealed class WidgetRepository
{
    private readonly IDatabaseExecutor _db;

    public WidgetRepository(IDatabaseExecutor db) => _db = db;

    public Task<Widget?> GetByIdAsync(string id, CancellationToken ct) =>
        _db.QuerySingleOrDefaultAsync<Widget>(
            "SELECT * FROM Widgets WHERE Id = @Id",
            new Dictionary<string, object?> { ["Id"] = id },
            cancellationToken: ct);
}
```

Consumers never new up a `SqlConnection` or `HanaConnection`, and never reference
`Microsoft.Data.SqlClient` or `Sap.Data.Hana` directly — only `APIPlatform.Data.*` abstractions.

## SQL portability (SQL Server + SAP HANA)

Code and SQL written against this package must stay portable across both engines:

- IDs and timestamps are generated by the API, not the database — no `IDENTITY`, `SEQUENCE`,
  `NEWID()`, or `GETDATE()`. Use `NVARCHAR(36)` for platform IDs.
- Avoid SQL Server-only constructs in portable SQL: `MERGE`, `OUTPUT INSERTED`, TVPs, SQL
  Server-specific JSON/XML functions.
- Paging, identifier quoting, and other syntax differences belong in a small dialect abstraction
  at the call site (e.g. `APIPlatform.CrudEngine.Sql.Dialects.ISqlDialect`) — never as a branch
  inside this package.

## Known limitations

- Only `SqlServer` and `Hana` are implemented. The `DatabaseProvider` enum intentionally carries
  no placeholder values for engines without a registered `IDatabaseProvider`.
- SAP HANA integration is verified at the abstraction/construction level only (provider
  resolution, connection type, DI wiring). Exercising it against a live HANA instance requires a
  reachable HANA server/cloud instance and is out of scope for this package's unit tests — see
  `APIPlatform.Database.Tests`.
- **Parameter marker syntax is not identical between engines.** Dapper forwards whichever prefix
  character (`@`, `:`, or `?`) your SQL text already uses straight through to the ADO.NET
  parameter — it does not translate between conventions. `Microsoft.Data.SqlClient` requires
  `@name`. SAP HANA's client historically expects `:name`-style markers; confirm the exact
  convention against the `Sap.Data.Hana.Net` version in use before pointing HANA-targeted SQL at
  this executor. This is a genuine SQL-text difference, not something the executor can paper
  over — keep engine-specific SQL text (or a dialect abstraction, as CrudEngine already does for
  paging/quoting) at the call site rather than inside this package.
